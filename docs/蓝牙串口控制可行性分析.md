# 蓝牙串口控制 —— 可行性分析

> 结论先说：**完全可以实现，而且不需要动 CubeMX、不需要加 RX DMA、中断优先级一行都不用改。**
> 但有 3 个"坑"必须先处理，否则功能会看起来"没反应"。

---

## 1. 现有串口状态（已逐项核对代码与 .ioc）

| 项目 | 现状 | 出处 |
|---|---|---|
| 外设 / 引脚 | USART1，PA9 = TX，PA10 = RX | `BNGU_Light.ioc` |
| 参数 | **115200**，8 数据位，1 停止位，无校验 | `Core/Src/main.c` `huart1.Init.*` |
| 模式 | `UART_MODE_TX_RX` —— **RX 硬件已经配好了** | 同上 |
| 发送通道 | DMA1_Channel4（内存→外设，BYTE，NORMAL，低优先级） | `.ioc` `Dma.USART1_TX.0.*` |
| 发送软件 | `App/telemetry.c`：单份静态缓冲 + 忙标志 + 1s 看门狗 | `telemetry.c` |
| **接收通道** | **软件里完全没有启动接收** —— 没有任何 `HAL_UART_Receive_*` 调用 | 全工程搜索确认 |
| USART1 中断 | **已使能**，抢占优先级 3、子优先级 0 | `stm32f1xx_hal_msp.c:324` |

也就是说：**接收的硬件通路是通的，只是软件从来没去读**。收到的字节进 DR 寄存器、置 RXNE 标志，因为没人读、也没开 RXNEIE，硬件会把它们丢掉（置 ORE 溢出标志），对现有功能没有任何影响。

所以这个功能是"**补上一条早就留好的路**"，不是"改架构"。

## 2. 需不需要加 DMA 或中断？

### 结论：**需要"接收中断"，不需要"接收 DMA"。**

推荐用 **`HAL_UARTEx_ReceiveToIdle_IT()`**（接收直到空闲）。我已确认这个 API 在当前 HAL 里存在（`stm32f1xx_hal_driver/Inc/stm32f1xx_hal_uart.h`）：

```c
HAL_StatusTypeDef HAL_UARTEx_ReceiveToIdle_IT(UART_HandleTypeDef *huart,
                                              uint8_t *pData, uint16_t Size);
```

它比逐字节 `HAL_UART_Receive_IT()` 好在两点：

1. **不用应用层反复重新武装**（HAL 内部自己续），不会因为主循环慢而丢字节；
2. **自带 IDLE 空闲线检测** —— 串口线上安静一个字节时间就回调一次，天然给出"一帧结束"。
   于是**手机端不发换行也能解析指令**，对蓝牙串口 App 特别友好。

### 代价算给你看

| | 数值 |
|---|---|
| 115200 下的字节率 | 11520 字节/s |
| 每个字节一次中断 | ≈ 4µs（-O0，含 HAL 分派） |
| **连续满速收数据的 CPU 占用** | **≈ 4.6%** |
| 实际一条指令（`MODE3\r\n` = 7 字节） | **8 次中断 ≈ 32µs**（0.003% CPU 时间） |

**完全没有压力。** 遥测每 100ms 发一帧 ~85 字节的 DMA 传输（7.4ms）占的 CPU 都比它多。

### 什么情况下才需要 RX DMA

- 波特率提到 **460800 以上**，或者
- 蓝牙端持续高速回传数据（不是发指令，是流式数据）

那时再加 DMA1_Channel5（USART1_RX，CIRCULAR）+ IDLE 中断。**本项目不需要。**

> ⚠️ 注意：现在 CubeMX 里**没有**分配 USART1_RX 的 DMA 通道。如果以后要加，必须回 CubeMX 勾选并重新生成代码 —— 这也是我推荐用中断方案的原因之一：**零 CubeMX 改动**。

## 3. 中断优先级怎么配？

### 结论：**一行都不用改。现状正好是对的。**

现有优先级表（抢占优先级，数字越小越高）：

| 中断 | 抢占 | 子 | 作用 | 会不会被接收中断打扰 |
|---|---|---|---|---|
| `TIM1_UP_IRQn` | **0** | 0 | 1kHz 槽切换（含 TIM2 相位锁定） | 不会 —— 它可以打断接收中断 |
| `TIM2_IRQn` | **0** | 0 | 20kHz 阴极软件 PWM | 同上 |
| `TIM3_IRQn` | 1 | 0 | 100Hz 应用节拍 + 触发 ADC | 同上 |
| `DMA1_Channel1_IRQn` | 2 | 0 | ADC 循环 DMA | 同上 |
| `DMA1_Channel4_IRQn` | 2 | 0 | 串口发送 DMA | 同上 |
| **`USART1_IRQn`** | **3** | **0** | 串口收 / 发完成 | **全系统最低的抢占级** |
| `SysTick` | 15 | 0 | HAL 时基 | USART1 可以打断它 |

USART1 已经是**所有应用中断里最低的抢占优先级**，这正是我们要的：

- ✅ 它可以被 TIM1 / TIM2 / TIM3 / DMA 抢占 → **接收中断永远不会延迟扫描**
- ✅ 它不会抢占任何扫描相关中断 → **不会造成槽错位、亮度抖动、残影**

### 最坏情况延迟还能不能收得住？

USART1 中断最坏要等所有高优先级中断跑完：

```
TIM1 槽切换 ≈ 3µs  +  TIM2 PWM ≈ 4µs  +  TIM3 ≈ 2µs  +  2 个 DMA ≈ 4µs
                                    ≈ 13µs
```

| 波特率 | 一个字节的时间 | 13µs 延迟够不够 |
|---|---|---|
| **115200（当前）** | **87µs** | ✅ 余量 6.7 倍 |
| 230400 | 43µs | ✅ 余量 3.3 倍 |
| 460800 | 21.7µs | ⚠️ 勉强，建议改 RX DMA |
| 921600 | 10.8µs | ❌ 会丢字节，必须上 RX DMA |

**所以 115200 下中断方案是安全的。**

### 如果以后加 RX DMA

优先级照抄发送 DMA 那一档即可：**`DMA1_Channel5_IRQn` 抢占 2、子 0**，USART1 保持 3 不变。

## 4. 指令集与"哪些数据有效"

### 建议的指令格式

不区分大小写；结尾的 `\r` / `\n` / 都不要（靠 IDLE）都能识别。

| 指令 | 有效范围 | 作用 |
|---|---|---|
| `MODE<n>` | **n = 1 ~ 5** | 切换模式。复用 `effects_request_mode()`，所以会**闪 n 下**做视觉确认，和按 KEY2 完全一致 |
| `BRIGHT<n>` | **n = 0 ~ 100** | 亮度峰值百分比。走**和电位器完全相同**的平方律，映射到内部 4 ~ 19 级 |
| `SPEED<n>` | **n = 0 ~ 100** | 速度百分比。走**和电位器完全相同**的等比表，映射到内部 2 ~ 50 |
| `TLM<0\|1>` | 0 或 1 | 关/开 10Hz 遥测（**强烈建议加，理由见 §6(b)**） |
| `STATUS` | — | 回读一行当前状态 |
| `HELP` | — | 回读指令表 |

**为什么 SPEED / BRIGHT 用百分比而不是内部原始值：**

- 内部值不好用：`BRIGHT=4..19` 是非线性的（平方律），`SPEED=2..50` 也是非线性的（等比），直接给数字手感是歪的；
- 百分比和电位器共用同一套映射函数，**蓝牙设 50% 和电位器拧到中间是完全一样的效果**；
- 遥测帧里同时报了百分比和内部值，方便核对。

> 如果你更想直接发内部值（比如 `BRIGHT15` 就是 15 级），改一个常量就行 —— 但那样 15 和 16 的视觉差会比 15% 和 16% 大很多，手感不均匀。

### 举例

| 发送 | 结果 |
|---|---|
| `MODE3` | 切到同步呼吸，屏幕闪 3 下 |
| `BRIGHT80` | 亮度峰值 = 4 + 15×0.8² ≈ 13 级，遥测里 `BRIGHT=13/19` |
| `SPEED30` | 速度 = 查表得 19（190ms/点） |
| `TLM0` | 停掉 10Hz 遥测，手机端界面清静 |
| `STATUS` | `[BT  ] MODE=3(BREATH) BRIGHT=13/19 SPEED=19 POT=BOTH PWR=ARMED` |

## 5. 无效输入怎么回包

所有回复走**现有的遥测发送通道**（同一份静态缓冲 +忙标志），标签用 `[BT  ]`，和 `[TLM ]` / `[M1  ]` 这些区分开。

| 情况 | 回复 |
|---|---|
| **成功** | `[BT  ] OK MODE=3(BREATH) BRIGHT=13/19 SPEED=19` |
| **未知指令** | `[BT  ] ERR unknown 'FOO'  \|  MODE<n> 1..5  SPEED<n> 0..100  BRIGHT<n> 0..100  TLM<0\|1>  STATUS  HELP` |
| **数值越界** | `[BT  ] ERR MODE=9 out of range 1..5` |
| | `[BT  ] ERR BRIGHT=-3 out of range 0..100` |
| **缺数值** | `[BT  ] ERR MODE needs a number  (MODE1..MODE5)` |
| **行太长** | `[BT  ] ERR line too long (max 16)` |
| **收到 HELP** | `[BT  ] MODE<n> n=1..5  \|  SPEED<n> n=0..100  \|  BRIGHT<n> n=0..100  \|  TLM<0\|1>  \|  STATUS  \|  HELP` |

原则：**错在哪就说哪，并把这一条指令的合法范围直接写出来** —— 手机上是小屏幕，不用再去翻文档。

## 6. 三个必须先处理的坑

### (a) 电位器会在 10ms 后把蓝牙设的值冲掉 ⚠️

`effects_tick()` 每 10ms 调一次 `pot_update()`，软接管一旦处于"跟手"状态，它就会用 ADC 读数**覆盖** `g_bright` / `g_speed`。所以 `BRIGHT50` 发下去，10ms 后就没了 —— 表现为"**发了没反应**"。

**解法（1 行）**：蓝牙改完参数后调用现成的 **`pot_freeze()`**。
这正是 Phase B 为 KEY3 换档做的软接管：值先冻住，等你真的转动电位器（超过 5%）才重新跟手。

- 蓝牙发的值会**稳定生效** ✅
- 之后一拧电位器，控制权自然交回旋钮 ✅
- 和"按 KEY3 换档""切模式"的行为完全一致，用户不会觉得两套逻辑打架 ✅

### (b) 10Hz 遥测会把手机界面刷爆 ⚠️

遥测每 100ms 一帧、约 85 字节 → **约 850 字节/秒**。手机蓝牙串口 App 打开就是满屏滚动，指令回包会被淹没。

**解法**：加 `TLM0` / `TLM1` 开关。调试时开、演示时关。
（另一个选择是把遥测降到 1~2Hz，但那样就失去了示波器式的观感，不如做成开关。）

### (c) PA10 会被两个发送端同时驱动 ⚠️（硬件）

这是**引脚层面**的问题，比软件更需要注意：

```
PA9  (MCU TX)  →  USB-TTL 的 RX   +   蓝牙模块的 RX     ✅ 一个输出带两个输入，没问题
PA10 (MCU RX)  ←  USB-TTL 的 TX   +   蓝牙模块的 TX     ❌ 两个推挽输出对打
```

**而且没有第二个串口可以用**（我把全部引脚核对了一遍）：

| 备用串口 | 引脚 | 能不能用 |
|---|---|---|
| USART2 | PA2 / PA3 | ❌ 两个都是 LED 阴极 L1 / L2 |
| USART3 | PB10 / PB11 | ❌ PB11 是 KEY1（电源自锁） |

所以 USART1 必须**共用**。推荐做法：

1. **首选**：烧录走 SWD（你现在就是），所以 PA9/PA10 不需要给 bootloader 用；
   把蓝牙模块接 PA9+PA10，PC 端如果还想看，**只接 USB-TTL 的 RX 到 PA9、TX 悬空**。
   这样 MCU 的 RX 只有蓝牙一个驱动源 ✅
2. 或者两条 TX 线上各串一个 **1kΩ 电阻**，让对打时电流受限（不推荐，但能凑合）。

> 附带说明：PA9/PA10 也是 STM32 内置 bootloader 的串口。蓝牙模块在复位瞬间如果往 PA10 灌数据，理论上可能影响进 bootloader —— 但你用 SWD 烧录，这条不成立 ✅

## 7. 还有几个小交互要定

| 场景 | 建议行为 |
|---|---|
| 显示处于**黑屏待机**（等按键）时收到 `MODE2` | **唤醒并切到 MODE2**（否则用户会以为蓝牙坏了） |
| **开机动画**期间收到 `MODE` 指令 | 正常允许 —— `do_switch()` 本来就会清掉动画标志 ✅ 不用额外处理 |
| 收到 `MODE` 但**它已经是当前模式** | 回 `OK` 但不闪灯（避免无意义的闪） |
| **波特率** | 固件是 115200。HC-05/06 出厂默认 **9600**，必须先用 AT 指令改成 115200（`AT+UART=115200,0,0`）；有些 BLE 模块（JDY-31 / HM-10）默认就是 9600 或 115200，查一下模块手册 |
| 模块**供电** | HC-05/06 的 VCC 要 **3.6~6V**（不能只给 3.3V），但信号是 3.3V 电平，直连 STM32 没问题；BLE 模块一般 3.3V 供电。按模块手册来 |
| **行长度上限** | 定 16 字节。收到的垃圾数据（比如蓝牙建立连接时的杂波）超长就丢弃并回 `ERR line too long`，防止缓冲溢出 |
| **收发状态独立性** | 已确认当前 HAL 的 `UART_HandleTypeDef` 里 `gState`（发送）和 `RxState`（接收）是**两个独立字段** → 接收中断和发送 DMA 可以同时工作，不会互相报 HAL_BUSY ✅ |

## 8. 实现方案（本次只分析，不写代码）

### 新增 1 个模块

```
App/cli.c / App/cli.h        ← 全部新代码都在这里
    cli_init()                启动 HAL_UARTEx_ReceiveToIdle_IT
    cli_tick()                100Hz 从 app_tick() 调用：解析 + 执行 + 回包
    HAL_UARTEx_RxEventCallback()   中断上下文：只往行缓冲塞字节、置"整行就绪"标志
    HAL_UART_ErrorCallback()       出错后必须重新武装接收（否则收完一次错就永久静默）
```

**解析放在主循环（100Hz），不放中断里** —— 和现在"中断只置标志、主循环做事"的架构一致，这样在中断里下断点也不会打乱 PWM。

### 改动清单

| 文件 | 改什么 | 量级 |
|---|---|---|
| `App/cli.c` `.h` | 新增 | ~250 行 |
| `App/app_config.h` | 加 4~5 个常量（行缓冲长度、最大行长、指令超时） | 10 行 |
| `App/effects.c/.h` | 暴露两个薄封装：`effects_set_bright_pct()` / `effects_set_speed_pct()`（内部就是现成的 `pct_to_bright/pct_to_speed` + `pot_freeze`） | 20 行 |
| `App/app.c` | `cli_init()` + `app_tick()` 里加 `cli_tick()` | 3 行 |
| `App/telemetry.c` | 错误回调里**同时**重新武装 RX；加遥测静音开关 | 10 行 |
| **CubeMX / .ioc** | **不动** ✅ | 0 |

### 资源预估

| | 预估 |
|---|---|
| Flash | **+1.5 ~ 2 KB**（现在用了 43.9%，很宽裕） |
| RAM | **+120 ~ 180 B**（现在 18.8%，也很宽裕） |
| CPU | 常态 **+0%**（没数据就没中断）；一条指令 ≈ 32µs 中断 + 主循环解析 <20µs |

### 工作量

**约 1 小时**（写 + 编译 + 串口助手联调）。

## 9. 一句话总结

| 你的问题 | 答案 |
|---|---|
| 能不能实现？ | **能。** 而且是"补上早就留好的通路"，不动架构、不动 CubeMX |
| 要不要加 DMA？ | **不用。** 115200 下中断方案的 CPU 占用约 4.6%，遥测的 DMA 占用都比它高 |
| 要不要加中断？ | **要。** 用 `HAL_UARTEx_ReceiveToIdle_IT()`，不逐字节恶补、还自带帧结束检测 |
| 优先级怎么配？ | **不用改。** `USART1_IRQn` 现在就是抢占 3（全系统最低），正好"只被打断、不打断别人"，绝不会影响扫描时序。以后真上 RX DMA 就照抄发送 DMA 的抢占 2 |
| 哪些数据有效？ | `MODE1..5`、`BRIGHT0..100`、`SPEED0..100`、`TLM0/1`、`STATUS`、`HELP` |
| 无效输入怎么办？ | 回 `[BT  ] ERR <具体原因> out of range <合法范围>`，未知指令直接把整张指令表回过去 |
| 最容易踩的坑 | **① 电位器 10ms 后冲掉蓝牙设的值（用 `pot_freeze()` 解决）② 10Hz 遥测刷爆手机（加 `TLM0`）③ PA10 被 USB-TTL 和蓝牙同时驱动（PC 端 TX 悬空）** |
